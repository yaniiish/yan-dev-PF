# GIT_WORKFLOW.md — yan-dev

> Workflow Git **obligatoire** pour le projet. Claude Code suit ce fichier à la lettre. Aucune exception sans validation explicite de Yan.

---

## 1. Principe

- `main` est **toujours déployable**. Rien n'est poussé directement dessus.
- Chaque tâche (section, fix, chore) se fait sur une **branche dédiée**.
- Quand Yan **valide une étape**, on merge la branche dans `main` (via fast-forward ou merge no-ff selon le cas), puis on supprime la branche locale.
- Pas de force-push sur `main`. Jamais.

---

## 2. Convention de nommage des branches

Format : `<type>/<scope>-<court-descripteur-kebab>`

| Type | Quand | Exemple |
|------|-------|---------|
| `feat/` | Nouvelle section, nouveau composant, nouvelle feature | `feat/hero-section` |
| `fix/` | Correction de bug ou de comportement | `fix/navbar-mobile-overflow` |
| `chore/` | Setup, config, dépendances, refactor sans changement fonctionnel | `chore/init-nextjs` |
| `docs/` | Mise à jour de la doc (`.md`) | `docs/update-roadmap` |
| `style/` | Ajustement purement visuel (CSS/Tailwind), pas de logique | `style/pricing-card-spacing` |
| `perf/` | Optimisation perf (bundle, images, lighthouse) | `perf/lazy-load-three` |

**Règles** :
- Lowercase strict, kebab-case, pas d'accent.
- Maximum ~50 caractères.
- Une branche = une seule tâche cohérente. Si tu touches deux sections différentes → deux branches.

---

## 3. Convention de commits

Format : `<type>: <message en français impératif présent, minuscule>`

| Type | Usage |
|------|-------|
| `feat` | Nouvelle fonctionnalité utilisateur |
| `fix` | Correction de bug |
| `chore` | Setup, deps, config |
| `docs` | Doc only |
| `style` | Formatting, espaces, CSS pur |
| `refactor` | Refacto sans changement fonctionnel |
| `perf` | Perf |
| `test` | Ajout / modif de tests |

**Exemples valides :**
- `feat: ajoute la section hero avec card de présentation`
- `feat: implémente le formulaire de contact avec validation zod`
- `fix: corrige l'overflow horizontal du falling pattern sur mobile`
- `chore: installe motion clsx tailwind-merge`
- `docs: met à jour la roadmap après validation hero`
- `style: ajuste les paddings de la card tarifs sur md`

**Règles** :
- En **français**, présent, impératif (`ajoute`, pas `ajouté` ni `ajouter`).
- Première ligne ≤ 72 caractères.
- Si nécessaire, sauter une ligne puis ajouter un corps avec plus de détails (pourquoi, et pas seulement quoi).
- **Pas d'emoji**.
- **Pas de mention "Generated by Claude" ni de co-author Claude** dans les commits. C'est Yan qui pousse, c'est Yan qui signe.

## 4. Cycle de vie d'une tâche

Workflow standard que Claude Code applique pour **chaque** tâche :

```bash
# 1. Vérifier qu'on est bien à jour sur main
git checkout main
git pull

# 2. Créer la branche de travail
git checkout -b feat/<scope>

# 3. Travailler — un ou plusieurs commits cohérents
# (Claude Code propose les commits, Yan valide / lance)
git add <fichiers ciblés, jamais `git add .` sans regarder>
git commit -m "feat: <message>"

# 4. (optionnel) Pousser sur le remote pour preview Vercel
git push -u origin feat/<scope>

# 5. ATTENDRE la validation visuelle/fonctionnelle de Yan
#    Voir §5 ci-dessous : Yan teste, donne le go ou demande des ajustements

# 6. Une fois validé par Yan, merge dans main
git checkout main
git pull
git merge --no-ff feat/<scope> -m "merge: feat/<scope> — <description courte>"
git push

# 7. Supprimer la branche locale et distante
git branch -d feat/<scope>
git push origin --delete feat/<scope>
```

### Pourquoi `--no-ff` ?
Le `--no-ff` (no fast-forward) crée un commit de merge explicite. Avantage : on voit clairement dans l'historique "ici on a livré la section hero". Sans `--no-ff`, Git ferait un fast-forward et la trace de la branche disparaît, c'est moins lisible pour un projet vitrine où on veut un historique propre par étape livrée.

## 5. Règle d'or : Claude Code ne merge JAMAIS sans validation

Claude Code peut :
- Créer la branche
- Faire les commits
- Pousser la branche (`git push -u origin <branche>`)
- **Préparer** la commande de merge

Claude Code ne peut PAS, sans validation explicite de Yan :
- `git merge` dans `main`
- `git push` sur `main`
- `git rebase` (sauf demande explicite)
- `git push --force` (jamais, sur aucune branche)
- Supprimer une branche distante

**Formulation attendue de Claude Code** après une étape terminée :

> "La branche `feat/hero-section` est prête et poussée. Tu peux la tester sur le preview Vercel. Quand tu valides, dis-moi 'go merge' et je merge dans main."

Yan doit explicitement dire **"go merge"** (ou équivalent clair) pour déclencher le merge.

## 8. Setup initial Git (à faire une seule fois)

```bash
# Init local
git init
git branch -m main   # forcer le nom 'main'

# Récupérer le .gitignore fourni dans le pack docs :
cp gitignore-template .gitignore
# (ou laisser create-next-app le générer et compléter manuellement)

# Premier commit
git add .
git commit -m "chore: init projet next.js avec tailwind v4"

# Lier au remote (GitHub privé recommandé)
git remote add origin git@github.com:<user>/yan-dev.git
git push -u origin main
```

> Le fichier `gitignore-template` à la racine du pack docs contient un `.gitignore` complet (Next.js + Node + Vercel + IDE + env files). À renommer en `.gitignore` dans le projet.

### Recommandations remote
- Repo **privé** sur GitHub (le code n'a pas besoin d'être public).
- Activer la **protection de branche `main`** dans les settings GitHub :
  - Require pull request before merging (optionnel si Yan travaille seul, mais utile comme sécurité)
  - Prevent direct push to `main`
  - Prevent force push

## 9. Si Yan veut un workflow Pull Request (plus carré)

Variante plus formelle (recommandée si Yan veut une revue claire avant chaque merge) :

```bash
# Au lieu du merge local en §4 étape 6, faire :
git push -u origin feat/<scope>
# puis ouvrir une PR sur GitHub :
gh pr create --base main --head feat/<scope> --title "feat: <titre>" --body "<description>"
# Yan review sur GitHub, puis merge depuis l'UI (squash ou merge commit selon préférence)
git checkout main && git pull
git branch -d feat/<scope>
```

**Avantages** : preview Vercel automatique par PR, historique de discussion sur la PR, possibilité d'annoter ligne par ligne.
**Inconvénient** : un peu plus de friction sur les petites tâches.

**Décision** : à confirmer par Yan. Par défaut, on part sur le merge local du §4. La PR reste possible à activer quand on veut.

## 10. Anti-patterns interdits

- `git add .` sans regarder ce qui est ajouté → toujours préférer `git add <fichier1> <fichier2>` ou `git add -p`
- Commits "wip", "test", "fix" sans contexte
- Commits qui mélangent plusieurs sujets (ex : "ajoute hero et corrige form") → splitter
- Travail directement sur `main`
- Merge sans validation Yan
- `git push --force` sur `main` ou sur une branche partagée
- Supprimer une branche distante sans confirmation
- Committer `.env.local`, `node_modules/`, `.next/`, fichiers IDE
