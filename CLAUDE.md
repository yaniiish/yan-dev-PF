## 1. Contexte du projet

**Nom commercial :** Yan-dev (micro-entreprise)
**Type de projet :** Site vitrine one-page (Next.js) servant de portfolio + tunnel de conversion.

**Objectif business :** Convertir deux profils de clients :
1. **Petits commerçants / artisans / indépendants** sans site ou avec un site daté → leur vendre un site vitrine simple, moderne, rapide à livrer, avec SEO local de base.
2. **TPE/PME ayant un besoin plus design** (entre-deux entre du WordPress générique et de l'awwwards.com) → leur vendre un site "premium" sur mesure.

**Tonalité visuelle :** Entre-deux entre rassurant (parle aux commerçants) et design (parle aux profils plus exigeants). Pas de jargon. Pas trop chargé. Pas trop minimal non plus.

**Stack figée :**
- Next.js (App Router) + React + TypeScript
- TailwindCSS v4 (variables CSS)
- **Motion** (anciennement Framer Motion) pour les animations
- Three.js + React Three Fiber (réservé à des éléments ponctuels, phase 2)
- Node.js pour le formulaire de contact (route API Next.js)
- Hébergement cible : Vercel (au moins en dev)

## 3. Règles de comportement Claude Code

### 3.1 Workflow
- **Plan avant code** : pour toute tâche de plus de ~30 lignes ou touchant plus d'un fichier, donner d'abord un plan court (3-6 puces) et attendre validation, sauf si je dis explicitement "go".
- **Petits diffs** : préférer plusieurs petites modifications vérifiables à un gros refactor.
- **Pas de dépendance ajoutée sans demander.** La stack est figée dans `ARCHITECTURE.md`.
- **Pas de fichier de configuration créé en doublon** (pas de second `tailwind.config`, pas de `.prettierrc` en plus si déjà géré, etc.). Vérifier avant.

### 3.2 Code
- **TypeScript strict.** Pas de `any` sauf justification en commentaire.
- **Composants serveur par défaut.** `"use client"` seulement si interactivité (state, event, motion, refs DOM).
- **Pas de CSS inline** sauf valeurs dynamiques calculées (ex : `style={{ transform: ... }}`).
- **Classes Tailwind ordonnées** : layout → spacing → typography → couleurs → effets → responsive.
- **Pas de couleurs en hex en dur dans les composants** → toujours via variables du design system (cf. `DESIGN_SYSTEM.md`).
- **Pas d'emoji dans le code livré** (UI, commits, commentaires).
- **Accessibilité minimale** : alt sur images, label sur inputs, focus visible, contraste AA.

### 3.3 Communication avec moi
- Réponses en français.
- Court et direct. Pas de "Bien sûr ! Voici..." ni de récap inutile en fin de réponse.
- Quand un choix est ouvert (ex : "easing de l'animation"), proposer 2 options brèves plutôt que décider seul.
- Si un fichier de spec contredit ma demande orale, **me le signaler** au lieu de trancher.

### 3.4 Git — workflow strict
Voir `GIT_WORKFLOW.md` pour le détail complet. Règles clés à retenir :
- **Une tâche = une branche** (`feat/<scope>`, `fix/<scope>`, `chore/<scope>`, etc.).
- Commits en **français, présent, impératif**, préfixés par `feat:`, `fix:`, `chore:`, `docs:`, etc.
- **Jamais de merge dans `main` sans validation explicite de Yan** ("go merge").
- **Jamais** de `git push --force` sur `main`.
- **Jamais** d'emoji, ni de mention "Generated by Claude", ni de co-author Claude dans les commits.
- Une étape de `ROADMAP.md` = une branche = un merge.
- Quand Claude Code termine une étape : pousser la branche, **arrêter**, demander la validation, attendre.
