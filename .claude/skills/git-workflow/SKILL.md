# Skill: git-workflow

## When to use
Every time you run a `git` command or are about to. Specifically:
- Starting a new task (create a branch)
- Finishing a unit of work (commit + push)
- Wrapping up a roadmap step (merge request to Yan)
- Any merge / rebase / push / branch operation

## Always read first
- `GIT_WORKFLOW.md` — full spec, source of truth
- `ROADMAP.md` — to know what step you're working on and which branch name applies

## Mandatory workflow for a new task

```bash
# 1. Always sync main first
git checkout main
git pull

# 2. Create the branch using the convention <type>/<scope>
#    type ∈ feat | fix | chore | docs | style | refactor | perf
git checkout -b feat/<scope>
```

Branch name rules:
- lowercase, kebab-case, no accents, no spaces
- max ~50 chars
- mapping ROADMAP step → branch name is in `GIT_WORKFLOW.md` §6

## Commit rules

Format: `<type>: <message en français, présent, impératif, minuscule>`

- ✅ `feat: ajoute la section hero avec card de présentation`
- ✅ `fix: corrige l'overflow horizontal du falling pattern sur mobile`
- ✅ `chore: installe motion clsx tailwind-merge`
- ❌ `Add hero section` (anglais)
- ❌ `feat: Ajouté la section hero` (passé composé)
- ❌ `feat: ajouter la section hero` (infinitif)
- ❌ `🚀 feat: hero` (emoji interdit)
- ❌ `feat: hero\n\n🤖 Generated with Claude Code\nCo-Authored-By: Claude <...>` (interdit absolu)

**Forbidden in commit messages and bodies:**
- Emojis of any kind
- "Generated with Claude" / "Generated by Claude" / "Made with Claude"
- `Co-Authored-By: Claude` or any Claude attribution
- Any AI-assistant mention

Yan is the sole author of every commit.

## Staging — never use `git add .` blindly

Always:
```bash
git status                    # see what's there
git add <fichier1> <fichier2> # explicit list
# OR
git add -p                    # interactive when many small changes
```

Never `git add .` or `git add -A` without first listing changes.

## Pushing

- Push to remote with `-u` the first time: `git push -u origin <branche>`
- Subsequent pushes: just `git push`
- **Force push:** absolutely forbidden on `main`. On a feature branch, only with Yan's explicit go-ahead and only with `--force-with-lease` (never plain `--force`).

## Finishing a step — the HARD STOP

After completing a task on a branch:

1. Run final checks: `pnpm typecheck && pnpm lint && pnpm build`
2. Push the branch
3. **STOP. Do not merge.** Instead, output exactly this kind of message to Yan:

> "La branche `feat/<scope>` est prête et poussée sur le remote. Résumé des changements :
> - <bullet 1>
> - <bullet 2>
>
> Tu peux la tester sur le preview Vercel (URL ...). Quand tu valides, dis-moi **'go merge'** et je merge dans `main`."

Wait for Yan's explicit "go merge" (or equivalent: "merge", "ok merge", "validé tu peux merger") **before** doing anything on `main`.

## Merging — only after explicit Yan approval

```bash
git checkout main
git pull
git merge --no-ff feat/<scope> -m "merge: feat/<scope> — <description courte>"
git push
git branch -d feat/<scope>
git push origin --delete feat/<scope>
```

`--no-ff` is **mandatory** (explicit merge commit, traceable history).

## Conflicts

If `git merge` raises a conflict:
1. STOP immediately.
2. List conflicted files in the chat.
3. Propose resolution per-file to Yan.
4. Do NOT auto-resolve.

## Things you NEVER do without Yan's explicit go

- `git merge` into `main`
- `git push` to `main`
- `git rebase` (even on a feature branch — rebases rewrite history)
- `git push --force` or `--force-with-lease` (anywhere)
- `git reset --hard` (destructive)
- Delete a remote branch
- Commit secrets (`.env.local`, API keys, tokens — check before staging)

## Self-check before any git command
- [ ] Did I read `GIT_WORKFLOW.md` if this is a non-trivial operation?
- [ ] Am I on the correct branch for this work? (`git branch --show-current` to confirm)
- [ ] If creating a branch: does the name follow `<type>/<scope>` convention?
- [ ] If committing: is the message in French, présent impératif, no emoji, no Claude mention?
- [ ] If staging: did I review what's being staged (no blind `git add .`)?
- [ ] If merging or pushing to main: did Yan explicitly say "go merge"?
- [ ] If anything destructive (force, reset, rebase): did Yan explicitly ask?

If any answer is "no" or "unsure" → STOP and ask Yan.
